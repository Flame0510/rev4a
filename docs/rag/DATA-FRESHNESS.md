# Data Freshness in Rev4a

> **Last updated:** 2026-09-13

Understanding how current the data in Rev4a is — and what is truly real-time vs. periodically updated.

---

## Session data

**Update frequency:** every 30 seconds

The daemon polls `openclaw sessions --json --all-agents` on a fixed 30-second
timer. Session statuses, token counts, and costs are therefore up to 30 seconds
behind reality.

The code declares a shorter 15-second interval for when a session is `working`,
but nothing uses it — the timer is always 30 seconds. Do not tell a user the
dashboard speeds up during active work.

**What this means for PULSE:** if you ask "is Argus working right now?", the
answer reflects data that is up to 30 seconds old.

---

## Event feed

**Update frequency:** every 5 seconds (via SSE stream)

The `/api/stream` endpoint pushes updates to the dashboard every 5 seconds. It
sends exactly three things:
- New events (spawn, complete, error, tool_call)
- The session list
- Today's cost total

Lineage is **not** pushed over the stream; the Lineage page fetches it itself.

The event feed is as close to real-time as Rev4a gets. However, events are
generated by the daemon's poll cycle, so an event that just happened may take up
to 30 seconds to appear, plus up to 5 more to reach the browser.

---

## System metrics (CPU, RAM, disk)

**Update frequency:** every daemon poll cycle (30 seconds)

**Retention:** 30 days (older rows are pruned automatically each cycle)

These metrics are collected and stored, and served by `GET /api/metrics`. They
are **not** shown on the dashboard — see the System Health note below.

---

## Cost totals

**Update frequency:** every 30 seconds (recalculated from sessions on each API call)

The cost figures shown in the dashboard are always computed fresh from the
database on each page load or SSE push. They are not cached.

**Cost override:** `/api/cost-override` exists, but no page in the dashboard
reads or writes it. There is no UI for setting one, so do not direct a user to
"the cost override screen".

---

## Cron jobs

**Update frequency:** on demand (fetched live from OpenClaw gateway on page load)

Cron status (last run, next run) is fetched directly from the OpenClaw gateway each time the Crons page is loaded. It is not stored in the database.

**Note:** if the OpenClaw gateway returns a scope-blocked error when listing crons, Rev4a may show no crons even if crons exist. This is an authorization scope issue, not a real absence of crons.

---

## Agent configuration

**Update frequency:** on demand (read from `openclaw.json` on each request)

The agents list, Telegram accounts, and bindings are read directly from
`openclaw.json` each time they are requested.

`GET /api/agents-config` serves this, but no page calls it — there is no "Agents
Config page". Per-agent settings are reached from the agent's detail panel on the
Agents page.

## Agent base image

**Update frequency:** polled every 2 seconds, continuously

`GET /api/agents/image-status` compares the local image digest with the remote
registry digest on ghcr.io. The banner polls it every 2 seconds for as long as the
page is open, not only while something is running.

The operation the banner triggers is a **`docker pull`**, not a build. While it
runs the banner shows an indeterminate animated bar: there is no percentage, no
byte count, and no log output in the UI. A log is written server-side to
`/tmp/rev4a-download-<timestamp>.log`, but nothing in the dashboard reads it.

---

## Memory / context files

**Update frequency:** on demand (files read from disk on each request)

Memory files are read from disk each time they are requested. There is no caching.

The tracked set is `USER.md`, `MEMORY.md`, `AGENTS.md`, `SOUL.md`, `HEARTBEAT.md`.

---

## What is NOT real-time

| Data | Why it may be stale |
|---|---|
| Cron sessions older than 7 days | The daemon prunes cron session rows after 7 days |
| Sessions never polled by daemon | If the daemon was down, sessions from that window are missing |
| Tool calls for a session | Only captured if the OpenClaw session export includes them |
| Costs before Rev4a was installed | Historical data before the first daemon run is not available |

---

## How to check if data is fresh

System health is a card on the **Dashboard**, not a page of its own. Its checks
cover session runtime, ingestion freshness, errors in the last 24 hours, today's
usage-based cost, and cron jobs. It reports no CPU, RAM, or disk figures.

To check directly on the server:
```bash
sqlite3 ~/.config/rev4a/data/events.db \
  "SELECT datetime(MAX(ts)/1000, 'unixepoch', 'localtime') FROM events"
```

The database lives under the Rev4a data directory, which defaults to
`~/.config/rev4a/` and moves with `REV4A_DATA_DIR`. It is not inside the repo.
